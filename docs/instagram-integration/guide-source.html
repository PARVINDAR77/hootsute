Executive Summary & Document Index

This technical manual provides a comprehensive, production-grade guide for integrating the official Meta Instagram Graph API into OmniSocial AI. The system architecture strictly preserves modular boundaries: Next.js App Router for frontend UI, NestJS API Gateway for business logic and OAuth orchestration, PostgreSQL 18 with Prisma ORM for relational persistence, and Redis with BullMQ workers for resilient, asynchronous post scheduling and dispatch.

Core Architectural Invariant: The Next.js client-side application must NEVER communicate directly with PostgreSQL or external Meta Graph APIs. All authorization exchanges, sensitive token storage, and media container dispatches are mediated exclusively by the NestJS backend API. Client Secrets and plaintext tokens are never transmitted to browser bundles.

CHAPTER 01 • INTRODUCTION

01 Introduction & Integration Fundamentals

Integrating the official Instagram API allows OmniSocial AI users to securely connect their professional Instagram presence, compose and preview platform-native media, schedule posts across time zones, and analyze engagement metrics without manual intervention or risky credential sharing.

What Instagram API Integration Means for a Multi-Tenant SaaS

Unlike personal social tools where an individual logs in directly, a B2B SaaS platform must support delegated, scoped authorization. Through the OAuth 2.0 protocol, an Instagram account holder grants OmniSocial AI specific capabilities (such as publishing images or reading insights) without disclosing their Instagram password. Our backend securely retains encrypted tokens and dispatches API commands on their behalf.

Instagram App vs Meta Developer App

Instagram Mobile App: Consumer client used by end-users to post photos and view feeds. Contains no developer credentials.

Meta Developer App: Cloud application registered on Meta's developer console representing OmniSocial AI. Holds our unique App ID and App Secret, manages redirect URIs, and configures requested scopes.

Instagram Login vs Facebook Login

Instagram Login (Route A): Authenticates directly using Instagram credentials. Does not require a linked Facebook Page. Ideal for pure Instagram creators.

Facebook Login (Route B): Authenticates via Facebook account and accesses Instagram through a connected Facebook Page. Required for enterprise multi-channel publishing.

CHAPTER 06 • OAUTH 2.0 INTEGRATION

06 Instagram OAuth 2.0 Integration Deep Dive

OAuth 2.0 is the foundational protocol that enables OmniSocial AI to act on behalf of a user without handling their credentials. The integration utilizes a multi-step exchange with CSRF protection and long-lived token upgrading.

Detailed 10-Step OAuth Sequence Breakdown

Phase Actor & Endpoint Action & Payload Description Security Verification
1-2 Next.js > NestJS
POST /oauth/initiate		 User clicks "Connect Instagram". NestJS generates cryptographically secure state: crypto.randomBytes(32).toString('hex'). State tied to active user ID and workspace ID in DB.
3-4 NestJS > Browser
Redirect to Meta		 Returns Meta OAuth Dialog URL with client_id, redirect_uri, state, and requested scopes. Strict 10-minute TTL on state record.
5-6 Meta > NestJS
GET /oauth/callback		 User grants permissions. Meta redirects to callback with code and state. NestJS verifies state exists and is unused. Prevents CSRF attacks; marks state as consumed.
7-8 NestJS > Meta
Token Exchange		 1. Exchange code for short-lived token (1h).
2. Exchange short-lived token for 60-day Long-Lived Token via oauth/access_token?grant_type=ig_exchange_token.		 Client Secret sent strictly over HTTPS server-to-server.
9-10 NestJS > PostgreSQL
Encryption & Save		 TokenVault encrypts long-lived token via AES-256-GCM. Upserts SocialAccount record in Prisma. Redirects user to dashboard. Plaintext token wiped from memory immediately.

CHAPTER 09 • SINGLE IMAGE PUBLISHING

09 First Instagram Image Publishing Workflow

Unlike simple social APIs that accept raw file uploads in a single HTTP request, Meta enforces a mandatory 2-step container lifecycle for all Instagram media publishing.

Technical Deep Dive: The 2-Step Container Lifecycle

Step 1: Create Media Container

Endpoint: POST /{ig-user-id}/media

Payload:

{
  "image_url": "https://s3.../photo.jpg",
  "caption": "Launch announcement! #ai",
  "access_token": "EAA..."
}

Meta downloads the image from your public HTTPS URL, validates dimensions, and allocates a temporary container ID (e.g. 17982038475).

Step 2: Publish Media Container

Endpoint: POST /{ig-user-id}/media_publish

Payload:

{
  "creation_id": "17982038475",
  "access_token": "EAA..."
}

Meta publishes the container to the live profile feed and returns the permanent Instagram Media ID (e.g. 18029384918).

CRITICAL PUBLISHING INVARIANTS:
1. Image URL Accessibility: The image must be hosted on a public HTTPS endpoint accessible by Meta's crawler (User-Agent: facebookexternalhit). Localhost URLs fail.
2. No Premature Status Updates: Never mark a post as PUBLISHED in OmniSocial AI until Step 2 returns HTTP 200 with a valid media ID.
3. Aspect Ratio Rules: Supported aspect ratios are strictly 4:5 (vertical 0.8) to 1.91:1 (horizontal). Images outside this ratio must be cropped before container creation.

CHAPTER 10 • CAROUSELS & REELS

10 Advanced Content Formats: Carousels & Reels

Beyond single static images, modern marketing requires multi-item Carousel sliders and short-form vertical Reels video. Each format builds upon the media container architecture with distinct encoding and polling requirements.

Multi-Item Carousel Publishing Flow (Up to 10 Items)

1. Create Child Containers

For each photo or video (2 to 10 items), call:

POST /{ig-user-id}/media

Parameters: is_carousel_item=true, image_url or video_url.

Collect all child container IDs: [id_1, id_2, id_3].

2. Create Parent Container & Publish

Create the parent carousel container:

POST /{ig-user-id}/media with media_type=CAROUSEL, children=[id_1, id_2, id_3], and caption.

Finally, call media_publish with parent container ID.

Instagram Reels & Video Specifications & Polling Loop

Specification Parameter Reels Requirement Engineering Implementation
Video Container & Codec MP4 or MOV container with H.264 video codec and AAC audio. FFmpeg transcoding pipeline validates before upload.
Aspect Ratio & Dimensions 9:16 vertical recommended (1080x1920 pixels). Min 720p. UI shows warning if horizontal aspect ratio detected.

Video Container Polling Logic

async function pollContainerReadiness(creationId, decryptedToken) {
  for (let attempt = 0; attempt < 30; attempt++) {
    const res = await fetch(`https://graph.facebook.com/v21.0/${creationId}?fields=status_code&access_token=${decryptedToken}`);
    const data = await res.json();
    if (data.status_code === 'FINISHED') return true;
    if (data.status_code === 'ERROR' || data.status_code === 'EXPIRED') {
      throw new Error(`Video processing failed with status: ${data.status_code}`);
    }
    await new Promise(r => setTimeout(r, 5000)); // 5s poll interval
  }
  throw new Error('Timeout waiting for Meta video container processing');
}

CHAPTER 11 • SCHEDULING & WORKERS

11 Scheduling & Redis Worker Pipeline

Automatic post publishing relies on OmniSocial AI's existing BullMQ and Redis infrastructure. The scheduling engine guarantees that posts execute at the exact customer-specified local time while handling network anomalies gracefully.

Key Scheduling Engine Architecture Principles

1. UTC Normalization

PostgreSQL stores all scheduledAt values in normalized UTC. The customer's IANA timezone (e.g. America/New_York) is preserved in timezone for daylight saving calculations.

2. Atomic Distributed Lock

Redis distributed locks (redlock key: lock:pub:{targetId}) prevent race conditions between clustered worker processes, guaranteeing zero duplicate posts.

3. Idempotent Retry

On network timeout, the PublishingReconciler checks if the post was already created on Instagram before executing a retry, preventing accidental double posting.

Architectural Safeguards for Multi-Account Broadcasts

Architectural Rule Technical Implementation Failure Prevention
Independent State Machine Each selected account receives a separate ScheduledPostTarget record in PostgreSQL with its own status lifecycle. Failure or rate-limit on Account A never cancels or marks Account B as failed.

CHAPTER 14 • WEBHOOKS & INBOX

14 Comments, Mentions & Webhook Automation

Real-time customer engagement requires listening to incoming comments and mentions via Meta Webhooks, verifying cryptographic payload signatures, and delivering responses through the unified OmniSocial AI Inbox.

Webhook Verification & Security Handshake

1. Verification Challenge (GET /webhooks)

When configuring webhooks in Meta dashboard, Meta sends a GET request:

GET /webhooks?hub.mode=subscribe&
hub.verify_token=my_secret_token&
hub.challenge=11582012

Backend validates hub.verify_token and echoes back hub.challenge with HTTP 200.

2. HMAC-SHA256 Signature (POST /webhooks)

Every event delivery contains the header:

X-Hub-Signature-256: sha256=a7f2...

Backend computes HMAC-SHA256 over raw request body using META_APP_SECRET and verifies using constant-time comparison.

CHAPTER 15 • SECURITY ARCHITECTURE

15 Security Architecture & Vault Hardening

Handling delegated social credentials requires bank-grade defense-in-depth. OmniSocial AI prevents token exfiltration, Cross-Site Request Forgery (CSRF), and Insecure Direct Object References (IDOR).

TokenVault AES-256-GCM Dual-Key Encryption Spec

Encryption Pipeline (TokenVaultService)

• Cipher: aes-256-gcm (Galois/Counter Mode).

• IV: 96-bit cryptographically unique random IV generated per token.

• Auth Tag: 128-bit authentication tag guarantees tamper resistance.

• Stored Format: v1:iv:authTag:encryptedData (Hex encoded).

Dual-Key Rotation Support

• TOKEN_ENCRYPTION_KEY (Primary): Encrypts all new tokens.

• TOKEN_ENCRYPTION_KEY_FALLBACK: Decrypts legacy keys during rotation.

• Zero-Downtime Migration: System automatically decrypts with fallback and re-encrypts with primary key upon read.
